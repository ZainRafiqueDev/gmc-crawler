# GMC Compliance Checker — Final Build Summary

A tool that takes a live e-commerce store URL, crawls it, and produces a Google Merchant Center (GMC) policy-compliance report — usable via CLI or a browser frontend, with optional recurring monitoring. Built from scratch across multiple sessions. This is the up-to-date, comprehensive record of everything built, why, and how it was validated — superseding the earlier `PROJECT_PROGRESS.md` snapshot.

---

## 1. Core pipeline

**Crawl → classify → check → report**, orchestrated as a LangGraph state machine (`app/graph.py`): `detect_platform → crawl_and_classify → deterministic_checks → llm_grading → compile_report`.

- **Platform detection** (`app/platform_detector.py`) — WordPress/WooCommerce or Shopify via REST API probes, falls back to generic/unknown. Checks operate on rendered DOM/text, not detected platform, so custom-built stores work identically.
- **Crawling** (`app/site_mapper.py`, `app/fetch.py`) — Playwright-driven, JS-rendered fetches, with:
  - Resilient retry with exponential backoff; `CANNOT_VERIFY` status after exhausting attempts (never silently "broken").
  - Sitemap discovery: `/sitemap.xml` first, falls back to `/wp-sitemap.xml` (WordPress core's own default).
  - **Two-tier crawl-priority seeding** (Store-Overview-first restructuring): sitemap URLs that look like Store Overview pages (policy pages, contact/business-identity) are seeded into the very first wave, ahead of Catalog URLs (products), which are themselves ahead of homepage-discovered nav links and everything else (collections, blog). A large-catalog store's category tree can no longer consume the crawl budget before the audit ever reaches a policy page or the contact page — verified live.
  - **URL canonicalization** (`app/url_canonicalize.py`) — WooCommerce-style filter/sort facet query params (`filter_color`, `query_type_*`, `on-sale`, `in-stock`, `on-backorder`, `featured`, and any custom attribute following the same prefix convention) are stripped before a discovered URL becomes the crawl's dedup key, so a store's color/size/stock/sale combinations of the same category page are never queued as separate fetches at all - the existing seen-URL set collapses them for free. Verified live: roughly half of a real 218-page crawl was facet-query duplicates of a dozen categories; after this fix, the same crawl budget reached genuinely distinct catalog pages instead. Pagination (`/page/N`) is deliberately still crawled (page 2+ can surface products page 1 doesn't link to) but grouped for *display* only (`canonical_page_key`) - see the report-structure section below.
  - robots.txt compliance (fail-open if unreachable), plus a hard-coded skip for cart-mutating action URLs (`?add-to-cart=`, etc.).
  - Anti-automation-detection hardening (realistic viewport/locale/`navigator.webdriver` spoofing) — a real host's bot-mitigation was found silently serving degraded content to a bare headless fingerprint; fixed.
- **Page classification** (`app/page_classifier.py`) — tags each page by type (product, collection, privacy/shipping/returns policy, terms of service, contact/about, FAQ, cart, checkout, blog/other). WooCommerce's default `/my-account` login/register page is explicitly URL-classified ahead of the text-based fallback - it was found live misclassifying itself as the store's *privacy policy* page, because its stock consent notice ("...described in our privacy policy") satisfied the text-based PRIVACY_POLICY rule. `/login`, `/register` handled the same way.

## 2. Checks

- **Deterministic checks** (`app/checks/deterministic.py`, `business_identity.py`, `woocommerce_products.py`, `shopify_products.py`, `generic_product.py`) — required-page presence, business identity/contact consistency, product data completeness. Verified against platform APIs where available; best-effort scraping otherwise, verification method always labeled.
- **Product image checks** (`app/checks/product_images.py`) — deterministic (broken links, missing alt text, size/format) plus vision-graded (watermarks, placeholder images, image/description mismatch). Images deduped by URL.
- **LLM-graded checks** (`app/llm/checks.py`) — judgment-based compliance (misleading claims, missing disclosures, editorial/professional quality, privacy-policy substance) via forced-schema tool calls, now grounded in real retrieved policy text (see Phase C).
- **Purchase-journey verification** (`app/checks/purchase_journey.py`) — opt-in, safety-critical add-to-cart → checkout walkthrough. Never submits real payment. Unit-tested; not yet validated against a live store's real checkout (documented gap, not claimed proven).
- **Form checks** (`app/checks/form_checks.py`, new) — structural checks on every contact/newsletter form found during the crawl: expected fields present (name/email/message for a contact form), submission endpoint doesn't 404/error, a soft heuristic for missing client-side email validation. **Never submits a real form** — read-only HTML parsing plus at most a GET (never POST) against the declared action URL. Built and validated live against a real WordPress/Contact-Form-7 site; found and fixed three real classification bugs along the way (see §9).
- **Duplicate product listings** (`app/checks/duplicate_products.py`, new) — flags the same (exact match, `Confidence.CONFIRMED`) or near-identical (`difflib.SequenceMatcher` ≥0.92, `Confidence.POTENTIAL_RISK`) product title appearing at more than one URL. Grounded as `quality_improvement` via `editorial_quality`'s own real retrieved RAG text, which names this exact scenario: *"The same product details being used for multiple products without differentiation."* Exact-match grouping is O(n); near-duplicate comparison is bounded to titles sharing the same first word, not a full O(n²) sweep of the whole catalog.

## 3. LLM layer

- `app/llm/client.py` defines a `Protocol` implemented for **Claude** (forced tool-use) and **OpenAI** (Structured Outputs), switchable via `LLM_PROVIDER`.
- `app/llm/cache.py` — content-hash-keyed cache wrapping either provider, backed by the DB. Reused for embeddings too (Phase C), not just grading calls.
- Tiered checking keeps real-world runs cheap (a 200-page real-store crawl used ~15 fresh LLM/vision calls total).

## 4. Phase C — real RAG policy index

Replaces the earlier hand-written stub policy summaries with a genuine retrieval index over the real GMC Help Center pages:

- **Sources**: 8 policy areas (`app/policy_watcher.py::POLICY_SOURCE_URLS`) — shipping, returns/refunds, business identity, misrepresentation, prohibited content, editorial quality, privacy policy, terms of service — each pointing at one or more real, confirmed `support.google.com/merchants/...` pages. The 3 areas that weren't obvious were researched and confirmed against the live pages, not guessed.
- **Pipeline**: heading-based chunker (`policy_chunker.py`) → OpenAI `text-embedding-3-small` embeddings, cached by content hash (`embeddings.py`) → SQLite storage (`PolicyChunk` table) → Python-side cosine-similarity retrieval with deduped citations (`policy_rag.py`).
- **Freshness**: `check_policy_sources` hash-diffs each source page independently of any store's schedule; a real change triggers a full re-chunk/re-embed and invalidates the LLM cache.
- **Validated live**: built a real 184-chunk index for $0.000369 total embedding spend; spot-checked citations directly against the live pages; proved the freshness/invalidation path end-to-end (seeded a stale hash, re-ran the watcher, confirmed real re-scrape and cache invalidation).

## 5. Suspension-risk classification (impact tier) — the core of the reporting redesign

**Problem this solves**: an early client ask was "only tell me about issues that could get the store's GMC account cancelled" — first solved with a blunt severity heuristic (Critical+High), then replaced with something actually grounded in Google's real enforcement model.

- **`ImpactTier`** (`app/models.py`): `suspension_risk` | `listing_disapproval` | `quality_improvement`, added to every `Finding`.
- **Grounding method** (`app/impact_tier.py`, `validation/impact_tier_grounding.md`): for each of the 8 policy areas, queried the real, live Phase C RAG index with "does this policy lead to item disapproval or account suspension?" and read the actual retrieved text — not an assumption:
  - **misrepresentation**: explicit — *"your Google accounts will be suspended upon detection and without prior warning."* Its best-practices section names business/contact-info accuracy and the "Unavailable offers" section carries the same consequence → grounds business-identity-consistency, missing required pages, non-functional cart/checkout, and broken contact/lead-gen forms as `suspension_risk`.
  - **prohibited_content**: disapproves individual ads by default but explicitly extends to *"suspending accounts for repeat or egregious violations"* → `suspension_risk`.
  - **shipping_policy** / product-data accuracy: entirely item-level (*"we'll disapprove your product"*), no suspension language → `listing_disapproval` for price/stock/availability mismatches.
  - **editorial_quality**: disapproval-only, no suspension language → `quality_improvement`.
  - Checks with no clean matching policy area (generic broken links, HTTPS issues, image mechanics) default to `listing_disapproval` — the cautious, still-visible choice — rather than guessing `quality_improvement`, and are flagged as ambiguous (`AMBIGUOUS_CHECK_IDS`).
  - **One classification was reconsidered mid-build**: `external_domain_link` was initially hypothesized as suspension-risk (per the brief's own starting hypothesis), but since that check fires once per individual link (including entirely benign ones, e.g. a social-media footer icon), tagging every instance as account-suspension risk would be an alarmist mismatch between a per-link finding and a site-wide policy concern — reclassified to `listing_disapproval` with the reasoning documented.
- **`major_only`** (the client-facing "show me only what matters" toggle) is now defined as: Critical severity, OR `impact_tier == suspension_risk`, excluding any `CANNOT_VERIFY` finding (unconfirmed issues never inflate the headline count).

## 6. Report structure

`app/report.py`, restructured around how the report is actually used, then given a full narrative pass on top:

1. **Header**, plus a **prominent API-verification recommendation** when a platform's REST API was detected but never authenticated (e.g. WooCommerce's route existing but returning 403) — names the exact env vars/CLI flags needed, not just a passive percentage buried in the stats.
2. **Prose Executive Summary** — a synthesized paragraph (store name, suspension-risk count, overall risk rating) instead of leading with bullets; the same severity/platform/SSRF/cache stats as before now live in an "At a Glance" subsection as supporting detail, alongside an **explainable Internal Audit Score** (0–100, HIGH/MEDIUM/LOW rating, itemized point-by-point deduction breakdown so the number is reproducible from the report's own findings) — explicitly labeled as an internal policy-risk score, **not a Google score and not a prediction of approval or suspension**.
3. **Suspension Risk Findings** (primary section) — every Critical finding plus every confirmed `suspension_risk`-tier finding, regardless of severity, in a **richer per-finding format**: Severity/Confidence/Verification/Page/Location/Evidence, Relevant Policy, **Specific Policy Requirement** (the real RAG-retrieved policy text the finding was graded against - `Finding.policy_requirement_text`, preserved instead of discarded once the citation string was built), **Why It Matters** (a plain-language consequence sentence derived from the finding's tier), Recommended Fix, and **Official Source** (the real GMC Help Center URL, extracted from the citation already embedded in `policy_reference` - not a new lookup).
4. **Policy-by-Policy Review** (new) — a table, one row per each of the 8 RAG-indexed policy areas (shipping, returns/refunds, business identity, misrepresentation, prohibited content, privacy policy, terms of service, editorial quality): Status (Pass/At Risk/Cannot Verify), finding count, one-line summary. Attribution (`app.impact_tier.policy_area_for_finding`) is a distinct axis from suspension-tier grounding - e.g. business-identity checks are tier-grounded via misrepresentation's best-practices text but attributed to their own "Business Identity" row here.
5. **Other Findings (Lower Priority)** (secondary, deprioritized but never dropped) — everything else, grouped by tier. Verified live: total findings always equals suspension-risk count + other-findings count exactly — nothing silently disappears, only reorganized by visual prominence.
6. **Page-by-Page Findings**, split into **Store Overview** (homepage, policies, contact, cart/checkout, FAQ, blog - still one entry per page, each now also showing a count of any lower-tier findings not itemized in the suspension-risk-only view) then a **grouped Catalog Overview** (products/collections, grouped by canonical logical page after URL-canonicalization collapses pagination for display - only groups with a displayed finding are itemized individually, everything else rolled into one summary line with its own lower-tier-finding count, never silently hidden). Verified live: a real 1381-line full report's suspension-risk-only view is 159 lines (~89% shorter) after this restructuring.
7. **Required Fixes (Prioritized)** — strictly the same predicate as the Suspension Risk Findings section (`is_suspension_risk_finding`, not a separate "or severity in Critical/High" clause) - see the bug this fixes in §12.
8. **Final Assessment** (new) — a closing paragraph: overall risk level (the same Internal Audit Score/rating), the single most important next action (the highest-priority suspension-risk fix, if any), and an honest limitations note (pages that couldn't be verified, findings that are best-effort vs. API-verified).

`major_only=True` renders sections 3-4 plus a summary of what's hidden (not 5-6 in full); `generate_delta_report` uses the same suspension-risk definition for consistency between full and delta reports.

## 7. Exports — Markdown, Word, PDF

- **Markdown** — the canonical format, everything above.
- **Word (`report_docx.py`)** and **PDF (`report_pdf.py`)** — both reuse the same markdown-parsing structure (no separate rendering path), both now use a single sans-serif family throughout (Arial in docx, Helvetica — metrically identical — in PDF, no font embedding needed), consistent heading hierarchy, formal 1-inch margins, and severity-colored text (red/orange/amber/gray) matching the web report's pills. A real docx bug (literal `&amp;` from double-escaping sanitized content) was found and fixed early on and carried correctly into the PDF exporter from the start.
- **Real markdown tables** — the Policy-by-Policy Review matrix (above) is the first markdown table this project generates, and both exporters used to fall through to raw pipe-delimited plain text for it (`| Policy Area | Status |...` shown literally). Both now detect a table block (a header row + `| --- |` separator) and render an actual `docx`/reportlab table, styled consistently with the rest of the document.
- Every download endpoint (`report.md`/`.docx`/`.pdf`, ad-hoc and per-monitored-store) accepts `?major_only=true`.

## 8. Monitoring subsystem

- `app/monitor_service.py` + `app/db.py` — register a store for `interval`, `on_change`, or both. On-demand "Re-run audit now" reuses the exact same pipeline and produces a delta report against the store's previous run.
- `app/policy_watcher.py` — independently tracks the real GMC policy pages on its own schedule (also the freshness mechanism behind Phase C's index).
- Both `report_markdown` and `report_markdown_major_only` are computed once at audit time and persisted, so the toggle never re-crawls or re-grades.

## 9. Security hardening

- **SSRF protection** (`app/security/ssrf_guard.py`) — three layers on every fetch, unconditionally: upfront URL validation, per-request re-validation (custom httpx transport + Playwright route guard), and a post-navigation final-URL check. Blocks private/loopback/link-local/reserved/multicast ranges including the cloud metadata endpoint. Every fetch reports positive, countable confirmation the guard ran.
  - A real Chromium/CDP corruption bug (`route.continue_()` truncating a real store's response) was found and fixed (`route.fetch()`/`route.fulfill()`), verified live and with a dedicated test.
  - **`DNSResolutionError`** — a distinct exception, separate from "this host resolves to a blocked address" (`SSRFBlockedError`), for when the resolver itself transiently fails (NXDOMAIN, a local/ISP DNS hiccup). `resolve_all_ips` (the single choke point every `assert_public_url` caller goes through - the CLI's upfront check, store registration, API job creation, and every per-page/per-request fetch) now retries a transient failure a few times before giving up, instead of the old behavior of instantly treating it as a permanent, non-retried security block. Found live, twice: once causing a per-page crawl false-positive (see §12), once aborting an entire audit at the CLI's one-shot upfront gate on a store that resolved fine moments before and after.
- **Rate limiting**, **hard resource ceilings** (pages/depth/concurrency/timeout/image size), **report sanitization** (every scraped field HTML-escaped before rendering — verified against real `<script>`/`<img onerror>` payloads), robots.txt + identifiable User-Agent, no secrets logged.

## 10. Frontend

- FastAPI backend (`app/api/main.py`) — job-based audit creation with live phase polling, Markdown/docx/PDF downloads, monitoring CRUD, discovery-independent job/report persistence (survives a backend restart mid-audit, verified live by killing the process mid-run).
- Next.js app (`frontend/`) — **Home**, **Report**, **Monitored Stores**, **Store Report** screens.
- **Visual redesign**: dual-color (indigo→fuchsia) brand palette, glassmorphic cards, an animated ambient background, Framer Motion entrance/stagger animations and micro-interactions throughout, an animated major-only toggle switch, severity-colored pills in the rendered report, and a collapsible "Other Findings" panel (collapsed by default) so the suspension-risk section reads as the primary view.
- Verified live in-browser end-to-end, including the new suspension-risk stat card, the Store-Overview-before-Catalog page ordering, and the collapse/expand interaction — confirmed via direct DOM inspection when an automation-only rendering artifact (a backgrounded tab throttling the entrance animation, not a real bug) made a screenshot briefly misleading.

## 12. Real-world validation — bugs found and fixed live, not just unit-tested

- **iana.org** — stress-tested report rendering at scale (150 pages, 1273 findings); caught and fixed a real renderer freeze on very large reports.
- **britanniagifts.us** (real, live WooCommerce store) — the most-used real-world test case across sessions:
  - Found and fixed the bot-detection/viewport crawl issue and the SSRF guard's CDP corruption bug.
  - Confirmed (not "fixed," a genuinely out-of-scope WAF TLS-fingerprinting issue) that a small number of image-broken findings on this site are false positives from our own tooling being blocked, not real broken images — reported honestly.
  - **This round's live-discovered form-check bugs**, all found by actually running the new checks against this real site and reading the output, not assumed correct:
    1. Contact Form 7's `action="/page/#wpcf7-fN-oM"` is a same-page JS scroll anchor, not a distinct endpoint — probing it produced a false-positive 403 (bot-protection blocking a plain GET) on a page Playwright had just loaded fine. Fixed by detecting when the resolved action (fragment- and trailing-slash-normalized) equals the current page.
    2. WooCommerce's login form's "Username or email" label made it look like a 2-field newsletter signup. Fixed by treating a password field, or a login/register class/id, as a hard exclusion.
    3. WooCommerce's register form's identifying CSS class token (`woocommerce-form-register`) isn't first in the class list — a naive `class[0]` check missed it. Fixed by joining all class tokens.
    4. A sitewide footer newsletter widget ("SUBSCRIBE" button, single email field) rendering on the contact page was misclassified as a broken contact form, purely because of the page's URL-derived type. Fixed by checking explicit newsletter signals (button text/class) before falling back to page-type.
  - After all four fixes, a fresh audit against the same store showed a headline of 4 genuine suspension-risk findings (3 missing required policy pages, 1 real business-contact inconsistency) — down from a report inflated by the form-check false positives — with every one of the 78 total findings still present in the underlying data, just correctly prioritized.
  - **This round's live-discovered bugs**, all found by closely reading a real generated report against the live site, not assumed correct:
    1. **`/my-account` misclassified as the store's privacy policy page.** WooCommerce's default login/register page renders a stock consent notice ("...described in our privacy policy") that the text-based classifier fallback matched on. Fixed by URL-classifying `/my-account`/`/login`/`/register` explicitly, ahead of the text fallback (same pattern already used for `/cart`/`/checkout`).
    2. **Page-by-page vs. Required Fixes contradiction.** The misclassification above caused `check_policy_page_substance` to grade `/my-account`'s content against the privacy-policy requirement (it obviously failed), producing a HIGH-severity `llm_policy_substance_privacy_policy` finding - a *dynamic* check_id family (`f"llm_policy_substance_{policy_id}"`) the impact-tier classification module had never accounted for, so it silently defaulted to `listing_disapproval` and was invisible in the suspension-risk page-by-page view - while `Required Fixes` still surfaced it via a leftover `or severity in (Critical, High)` clause from the pre-tier design. The same page showed "no suspension-risk issues found" and had a listed required fix simultaneously. Fixed on three layers: the classification bug (above), the missing tier classification (4 `llm_policy_substance_*` check_ids added, grounded the same way as `required_page_present` - a policy page with no real substance is functionally near-equivalent to a missing one), and `Required Fixes` now uses the exact same predicate as the Suspension Risk section, not a separate severity check.
    3. **DNS-resolution false positives, twice.** A transient DNS hiccup during a 218-page crawl caused the SSRF guard to report `blocked_ssrf` (a permanent, non-retried verdict) instead of a retriable failure for every page fetched afterward - three required policy pages that demonstrably exist (confirmed live: all return HTTP 200 with correct titles) were reported as "confirmed missing" instead of "could not be verified". Root-caused to `assert_public_url`'s DNS resolution and a genuine security block (resolves to a blocked IP) sharing one exception type; fixed with a new `DNSResolutionError` subclass, retried before giving up, everywhere `assert_public_url` is called - see §9. The same underlying class of bug then reappeared, once more, as a single-shot upfront gate (no retry loop at all) aborting a whole audit at `audit.py`'s pre-flight check; fixed at the shared root (`resolve_all_ips` itself retries now), not at each call site individually.
    4. **A closely related display bug**: an unreachable page (a real 404, or the above false positive) with no findings against it rendered as `[PASS]` in the page-by-page section - a status that means "checked, fine," not "couldn't load it." Fixed: `_page_status` now checks `page.reachable` before falling through to `PASS`.
    5. **Crawl budget wasted on facet-query duplicates.** Roughly half of a real 218-page crawl was WooCommerce filter/sort query-parameter variants (`?filter_color=`, `?on-sale=1`, etc.) of the same dozen category pages, each getting its own full page-by-page report entry despite being compliance-identical to the canonical URL. Fixed with crawl-time URL canonicalization (§1) plus report-time grouping of pagination variants (§6) - the same real store's suspension-risk-only report view dropped from ~1381 lines (full report) to 159 lines after the full restructuring.
- Total OpenAI spend across every real-store run to date: a handful of cheap calls plus the one-time $0.000369 embedding build — well under $0.05 all in.

## 13. Known gaps — documented, not hidden

- **Purchase-journey checks** — built, unit-tested, never run against a real store's live checkout.
- **No alerting webhook** — deferred pending the user's existing notification tooling elsewhere.
- **Frontend has no auth** — fine for local/internal use, not for open-internet exposure as-is.
- **A WAF TLS-fingerprinting issue** on at least one real tested store causes httpx-based image-integrity checks to report false "broken" positives; would require a TLS-fingerprint-spoofing HTTP client (separate scope). Partially addressable now via the opt-in proxy support added in §15 (routing through a different network can sidestep some IP-based instances of this), but not a TLS-fingerprint fix per se.
- **No "detect the complete absence of a contact form"** check — Part 2's form checks validate forms that exist; a contact page with *no* form at all (only a phone number, say) isn't flagged. A real gap surfaced while investigating the britanniagifts.us false positives (that site, in fact, has no genuine multi-field contact form anywhere — only a mislabeled newsletter widget) but out of the scope that was asked for this round.
- **Ambiguous impact-tier assignments** (`app.impact_tier.AMBIGUOUS_CHECK_IDS`) — generic broken-link/HTTPS/image-mechanics checks have no direct suspension-vs-disapproval grounding in the 8 indexed policy areas; defaulted to the cautious `listing_disapproval` tier rather than guessed, and explicitly flagged in code and in `validation/impact_tier_grounding.md`.
- **Duplicate-product-listing check (`app/checks/duplicate_products.py`) has thorough unit coverage (9 tests: exact/near-duplicate detection, title/heading preference, unreachable-page exclusion) but no fresh live confirmation against the exact real-world example that motivated it** (the same kayak listed at two britanniagifts.us URLs) - by the time this check was built, that specific store had started rate-limiting/bot-mitigating this session's many repeated crawls (transient DNS failures and HTTP 403s on a majority of requests, on a site confirmed reachable and returning 200 via `curl`/`nslookup` at the same moment). Continuing to hammer a real live store just to re-prove something already covered rigorously in isolation wasn't worth doing; documented honestly rather than claimed as live-proven.
- **Site rate-limiting from this session's own repeated crawls** — britanniagifts.us has been audited many times across this project's sessions; by this round it started intermittently rejecting requests (403s) and, separately, exhibited a few transient DNS resolution failures unrelated to the site itself (confirmed live: system DNS tools and `curl` succeeded immediately when the audit's own DNS resolution failed). The DNS side is now retried (see §9); the rate-limiting side is a reasonable real-world consequence of testing against the same live store repeatedly and not something to route around.

## 15. Broader real-world crawl robustness round (this round) — new work, built from scratch

Goal, stated explicitly up front and never contradicted anywhere in the report/UI copy: raise the real-world success rate across diverse real store setups, **and** guarantee that when a site genuinely can't be crawled, this tool fails safely and says exactly why — never fabricates a "missing"/"clean" verdict from an incomplete crawl. No universal-coverage claim is made or implied anywhere in this round's changes.

### 15.1 HTTP-status-aware retry/backoff (`app/fetch.py`)

- `FetchResult`/`CrawledPage` gained real failure categories instead of one generic "could not verify": `confirmed_not_found` (404/410, unchanged), `blocked_ssrf` (unchanged), **`rate_limited`** (429), **`likely_bot_blocked`** (403/401, or an anti-bot interstitial that never resolves), **`likely_captcha_blocked`** (a full-page CAPTCHA block specifically), **`network_error`** (DNS/connection/timeout-level failure, no HTTP response at all). `FetchResult.failure_category`/`CrawledPage.failure_category` expose one specific label; `app.fetch.FAILURE_CATEGORY_LABELS`/`_SHORT_LABELS`/`_RECOMMENDATIONS` are the single source of truth every check and the report draw from.
- **429**: reads `Retry-After` (seconds or HTTP-date, via `Response.header_value`) and backs off for that real duration (capped at `max_backoff_seconds`, default 30s) instead of the generic exponential schedule; falls back to exponential if the header is absent. Retries up to the normal `max_attempts`.
- **403/401**: capped at `max_bot_block_attempts` (default 2, deliberately lower than `max_attempts`) — never hammers an identical request against what's very likely a block.
- **404/410**: untouched, still confirmed-not-found, never retried.
- **503 and other 5xx**: confirmed still retries correctly (already worked; now under a named category for honest reporting rather than silent generic failure).
- **New per-domain minimum delay** (`_DomainThrottle` in `app/fetch.py`, `Settings.crawl_domain_min_delay_seconds`, default 0.5s, clamped [0, 30]) — reserves the next request slot under a lock so concurrent fetches to the same domain queue rather than burst, keeping this crawler's own pace from tripping a target's rate limiting. `PageFetcher`'s own default is 0.0 (opt-in) so direct callers/tests stay fast; `app.site_mapper.map_site` wires up the real configured value.
- 14 new/updated tests in `tests/test_fetch.py` cover all of the above (Retry-After honored and capped, 403 stopping short of `max_attempts`, 401 categorized the same as 403, 503 still recovering, network-timeout categorization, per-domain delay actually spacing out requests, and that the default stays a fast no-op).

### 15.2 Anti-bot interstitials and cookie-consent banners (`app/fetch.py`)

- **Confirmed the plain `networkidle` wait does NOT reliably cover a JS challenge interstitial** (a Cloudflare-style "checking your browser" page can sit network-idle for its whole multi-second countdown before it client-side-navigates) — made explicit with a dedicated step: after the normal load, if the captured HTML matches a known challenge/CAPTCHA signature (`_looks_like_challenge`/`_looks_like_captcha`), poll for up to `challenge_wait_seconds` (default 6s), re-checking `page.content()`, before deciding whether it resolved. If it resolves, the page is treated as a normal success (a stale first-navigation status code, e.g. a 503 challenge page, is not used to fail a page that demonstrably resolved to real content). If it never resolves: a CAPTCHA-specific signature → `captcha_blocked` (never retried — retrying doesn't solve a CAPTCHA); a generic interstitial → `bot_blocked` (subject to the same retry cap as 403/401).
- CAPTCHA detection is deliberately two-tier to avoid a false positive on any ordinary page that legitimately embeds a reCAPTCHA/hCaptcha/Turnstile widget in a contact form: a widget signature alone isn't enough — it only counts as a block when the page body is otherwise thin (`< 1200` visible chars) or an explicit "verify you're human"-style phrase is present. Unit-tested directly (`test_normal_page_with_embedded_recaptcha_widget_is_not_treated_as_blocked`) against a realistic contact-form fixture.
- **Cookie-consent dismissal** — confirmed the prior round only stripped consent-banner *text* for classification, never interacted with the page. Added `_dismiss_cookie_consent`: best-effort click of a recognized "Accept" control (OneTrust, Cookiebot, cookieconsent.js, CookieYes, and a handful of generic selectors/text patterns), run on every fetch before content is captured. Deliberately conservative (only clicks a control it's confident is "accept," never "reject") and fully swallows any failure — never breaks a fetch.
- **Live-validated, not just unit-tested**: a real Cloudflare JS-challenge demo page (`nowsecure.nl`, the standard public reference page for exactly this kind of testing) was fetched successfully end-to-end through the real pipeline.

### 15.5 CAPTCHA and proxy — the explicit ethical/practical line (Part 5)

- **CAPTCHA solving**: out of scope, never built. §15.2's CAPTCHA detection reports it (`captcha_blocked`, with an explicit "this tool never attempts to solve CAPTCHAs, by design" message and a recommendation to ask the merchant to allowlist the tool or do a manual check) — detection and honest reporting only.
- **Residential/rotating-proxy IP support**: flagged, not silently built, per the brief. After Parts 1–4 were live-tested, real evidence of IP/browser-fingerprint-level blocking turned up on major-brand sites that no amount of retry/backoff/politeness/interstitial-waiting could get through — `decathlon.fr` returned a clean HTTP 403 to a plain `curl` request but refused the TCP/TLS connection outright for headless Chromium from the same source IP (`net::ERR_FAILED`, no HTTP response at all); `tiendanimal.es` was reachable via `curl` (200) but not via headless Chromium at all, from the same machine. Brought back to the user as an explicit decision (not assumed) — the user chose to build it.
- **Built** (`app/proxy_config.py`, new): opt-in, off by default (empty settings = zero behavior change). BYO-proxy only — this project does not operate, harvest, or bundle any proxy infrastructure of its own; it lets an operator with their own legitimate proxy subscription point this tool at it, the same way robots.txt compliance and an honest, identifiable User-Agent are already built in rather than spoofed. Two shapes: a single rotating-residential gateway (`PROXY_SERVER`/`PROXY_USERNAME`/`PROXY_PASSWORD` — the provider rotates the exit IP server-side per new connection, and a fresh Playwright context is already opened per fetch attempt, so this rotates for free) or a client-side round-robin pool of distinct static endpoints (`PROXY_POOL`, comma-separated full URLs, takes precedence over `PROXY_SERVER`).
- Wired into both traffic paths: Playwright (`PageFetcher`'s `proxy_rotator`, a new context per attempt, real rotation across a multi-endpoint pool) and httpx (`app.security.ssrf_guard`'s `set_current_proxy`/`reset_current_proxy`, a `contextvars.ContextVar` — not a plain module global, so concurrent audits in the same process, e.g. the FastAPI backend running several jobs at once, never race each other's proxy setting — consulted automatically by `safe_async_client()`), set once per whole audit run in `app.graph.run_audit`/`run_audit_streaming` so platform detection (which runs before the crawl node) is consistent with everything after it.
- **The one non-negotiable**: the SSRF guard stays fully active regardless of proxy configuration. The proxy is configured directly on `SSRFSafeTransport` itself (not left to httpx's own separate proxy-mount mechanism), so the exact same transport instance that always validates the destination hostname first is the one that then makes the (possibly-proxied) connection — there is no code path where routing through a proxy skips that check. Directly tested (`test_ssrf_check_still_runs_when_a_proxy_is_configured`): the transport still raises `SSRFBlockedError` for a blocked address even with a proxy configured on it.
- 8 new tests in `tests/test_proxy_config.py`, 4 in `tests/test_ssrf_guard.py`, 2 in `tests/test_fetch.py`, 3 in `tests/test_graph_proxy_wiring.py`.

  - Grounded `suspension_risk` via `misrepresentation` (same pattern as business-identity inconsistency), per the brief's explicit instruction.
- **Part 4 — Citation freshness**: `app.llm.policy_rag.PolicyContext.verified_at` (the oldest `PolicyChunk.created_at` among the chunks actually cited - the more conservative value when a citation spans chunks verified at different times) threaded through to `Finding.policy_last_verified` and rendered as "Official Source: [url] (last verified: [date])" in both report formats, omitted gracefully when unknown (deterministic checks, stub-snippet fallback). ## 19. Fifth follow-up round — fixed-size LLM catalog sampling honesty + risk-weighted scaling

- **Part 1.1/1.2 — Coverage honesty**: `check_editorial_quality`/`check_prohibited_content` always sampled a flat first-5 product pages regardless of catalog size, with no disclosure anywhere in the report - a store with 500 products got the exact same "Pass" language as one with 5. New `LLMCoverageStats` model (`app/models.py`) threaded through `run_llm_checks` → `AuditState` (`app/graph.py`) → `generate_markdown_report` (`app/report.py`) → both CLI/API report-regeneration call sites. At a Glance now states e.g. "Prohibited-content / editorial-quality screening: 5 of 45 product page(s) checked (11%)"; the Policy-by-Policy matrix annotates an otherwise-clean sampled area as `Pass (partial coverage: N/M)` instead of a bare `Pass`. **Live-confirmed** against `meo.fr` (100-page crawl budget, 45 real reachable product pages found - britanniagifts.us and vellano.site were both unreachable this session, `network_error`, confirmed by direct probe before substituting): the generated report showed exactly `Prohibited-content / editorial-quality screening: 5 of 45 product page(s) checked (11%)` and `Prohibited Content | Pass (partial coverage: 5/45)`.
- **Part 1.3 — Sampling strategy decision**: presented three real-cost options via `AskUserQuestion`, priced from researched current gpt-4o-mini pricing ($0.150/1M input, $0.600/1M output tokens): (A) scale to catalog size capped at 50 (~10x cost on a large catalog), (B) keep the flat-5 sample but risk-weight which 5 (no cost change), (C) modest scale-up capped at 15 combined with risk-weighting (~3x cost on a large catalog, most coverage gain per dollar). **User chose Option C.**
  - Implemented in `app/llm/checks.py`: `_product_sample_size(total, cap)` = `min(cap, max(5, ceil(5% of reachable product pages)))`; new `Settings.llm_product_sample_cap` (default 15, hard ceiling 50 via `HARD_MAX_LLM_PRODUCT_SAMPLE` in `app/config.py`, same clamp-validator pattern as `crawl_max_pages`). `_select_product_sample()` replaces flat first-N-crawled with two cheap, already-available signals - no new brand watchlist or external data fetch: a price that's a rank-based bottom-decile outlier *within this store's own catalog* (deliberately relative, not an absolute threshold - "cheap" varies by store; rank-based rather than value-based specifically because real catalogs have many exact-tie prices, e.g. lots of `$X.99` items, which a value-threshold cutoff would over-match), and thin product copy (<40 words - less room to substantiate a claim). Ties keep crawl order for determinism.
  - Regression-tested: 25 tests in `tests/test_llm_checks.py` covering the sample-size formula at several catalog sizes, risk-weighted selection actually surfacing an outlier-priced and a thin-content page that were crawled last (not first), the cap holding at 15 for a 400-product synthetic catalog, and coverage stats reflecting the real scaled sample size end-to-end through `run_llm_checks`. Full suite: 419 passed.

## 20. Deployment guide + Dockerfile (free-tier hosting)

Live-researched (not from training knowledge) current 2026 free-tier terms for Render, Supabase, Vercel, and Railway before writing anything, since these change often and a stale claim here would be actively misleading. Wrote `DEPLOYMENT.md`, a root `Dockerfile` (based on Playwright's own maintained image so Chromium's system deps are present - Render's native Python buildpack doesn't have them), and `.dockerignore`.

Key honest finding, called out explicitly rather than glossed over: this app's scheduled store-monitoring feature (`APSchedulerBackend`, in-process, needs to keep running) is fundamentally in tension with how free tiers work - Render's free Web Service sleeps after 15 minutes idle, and Supabase's free Postgres project pauses after 7 days with zero DB activity. Documented both as real constraints with two honest ways to live with them (an external uptime-ping keep-alive, or accepting on-demand-audits-only and skipping scheduled monitoring), rather than presenting a fully-free stack as if it transparently supports always-on scheduling. Recommended stack: Vercel (frontend, Hobby/personal-use), Render free Web Service + Docker (backend), Supabase free Postgres (no pgvector extension needed - `app/llm/policy_rag.py` already does cosine similarity in Python over a plain float-array column, confirmed by re-reading the code before writing this, not assumed). Railway explicitly ruled out and documented as why (no real permanent free tier as of 2026 - 30-day trial then $1/month credit, not enough for an always-on Playwright container).
